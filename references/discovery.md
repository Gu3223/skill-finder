# 检索与核验策略

## 设计查询

从任务抽取动作、对象、输入/输出和决定性约束。先查功能，再扩展 skill、MCP、CLI 或库的实现方式。以下是查询模板，不是固定站点白名单：

| 目的 | 示例模板 |
| --- | --- |
| 找技能 | `site:github.com <task> "SKILL.md"`；`<task> agent skill` |
| 找工具 | `<task> <format> <constraint> open source`；`<task> CLI library` |
| 找集成 | `<service> official MCP server`；`<service> plugin integration` |
| 找替代品 | `<candidate> alternative <hard constraint>` |
| 找原始项目 | `<project> official documentation repository` |
| 核验限制 | `site:<official-domain> <feature> limitations requirements` |
| 核验成本 | `site:<official-domain> pricing quota license` |

中文任务通常同时用英文领域术语检索；保持语义一致。一次结果不足时换术语和来源，不只是翻页。至少考虑两条不同的发现路径；不要将未实际查过的来源写成已覆盖。若指定来源无法访问，交付可核验的其他结果并说明该缺口。

## 处理 GitHub 等代码托管来源

1. 搜索项目或代码并打开实际仓库；站内代码搜索需要登录时，可用允许的公开网页搜索定位文件。
2. 读取 README 或官方文档，再定位具体 skill 文件、入口、依赖声明、许可证及相关示例。单一仓库中可能存在多个互不兼容的技能。
3. 核对来源归属、默认分支/版本、归档情况、相关变更或问题；不要把仓库更新等同于目标组件仍可用。
4. 引用到实际项目、文档或 skill 文件；安装需要稳定性时记录标签或提交，禁止编造固定版本链接。
5. 原站读取受阻时区分“搜索定位”“阅读文档”“检查源码”“实际运行”四种证据，保留未知项。不通过猜测原始文件地址来假装验证完成。

## 比较框架

先判断是否通过硬约束，再做取舍；不使用缺乏依据的数值评分。

| 维度 | 要回答的问题 |
| --- | --- |
| 任务覆盖 | 能否完成目标输出？哪个步骤仍需人工或另一个组件？ |
| 效果证据 | 是维护者示例、可复现评测还是当前实测？样本是否类似？ |
| 环境 | 本机/云端/当前聊天在哪里运行？平台、GPU、网络和权限是否满足？ |
| 使用成本 | 安装、学习、运行、API、维护分别付出什么？免费层限制是什么？ |
| 可信与维护 | 来源是否可追溯？许可证、版本和相关问题是否清楚？ |
| 退出成本 | 数据能否导出？能否替换供应商、复现版本和撤销试用改动？ |

## 最低成本验证示例

- **扫描 PDF 表格**：用一个包含合并单元格和数字的真实代表页，核对表格结构、关键数值和所需人工修正；避免拿可复制文本的 PDF 代替扫描输入。
- **文献检索**：用一篇已知应能检出的论文和一个新查询，核对覆盖、DOI、引用出处与导出格式；检索数量不能代替相关性。
- **MCP/插件**：先核验宿主兼容和认证要求；获授权连接后用一条只读操作验证目标能力，不通过写操作试探权限。
- **Agent skill**：读取目标技能及依赖后，用一个最小代表任务检查是否可执行、是否依赖另一宿主，以及输出是否达到通过条件；安装成功不等于任务成功。
- **生成/转换工具**：先固定输入与成功标准，比较输出的可编辑性、格式保真和人工成本，不仅比较预览图。
